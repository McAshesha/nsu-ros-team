# ПР09. Причины ошибок baseline

Детектор `red-component-baseline-v1` и его пороги (`red_min 180`, `green_max 120`, `blue_max 120`, `min_area_px 2`) не менялись. Отчёты: `metrics-before.json` (разбиение из `manifest-leaky.json`, `--allow-leak`) и `metrics.json` (исправленное `data/manifest.json`).

| | До (утечка) | После |
|---|---|---|
| test | sample-03, sample-04 | sample-05, sample-06 |
| split_issues | 3 нарушения | нет |
| TP / FP / FN | 2 / 0 / 0 | 1 / 1 / 1 |
| precision / recall / F1 | 1.0 / 1.0 / 1.0 | 0.5 / 0.5 / 0.5 |
| mean_iou | 1.0 | 1.0 |

## 1. Утечка по capture_id

- Кадры: `sample-03` (capture-a) и `sample-04` (capture-b) стояли в test, а `sample-05` (capture-c) и `sample-06` (capture-d) — в calibration. По `split-contract.json` capture-a и capture-b целиком в calibration, capture-c и capture-d — в test.
- Влияние: в test попали два простых кадра с одним ярко-красным объектом в каждом, TP 2, FP 0, FN 0, F1 1.0. Трудные кадры ушли из оценки. После исправления TP 1, FP 1, FN 1, F1 0.5. Алгоритм не изменился — изменился только состав test, то есть 1.0 был свойством разбиения, а не детектора.
- Как обнаружить снова: evaluator без `--allow-leak` завершается с кодом 1 и пишет `split_issues` (`capture_id пересекаются между calibration и test` и ещё два нарушения контракта). В CI шаг `Recompute PR09 metrics` запускает evaluator без этого флага на `data/manifest.json`, поэтому манифест с утечкой не пройдёт.

## 2. Пропуск тёмного объекта

- Кадр: `sample-05`, размеченный объект `cone` в bbox `[1, 1, 3, 2]`.
- Причина: пиксели объекта `(160, 20, 20)`. Красный канал 160 меньше `red_min = 180`, маска пустая, детекций нет.
- Влияние: FN +1, recall падает до 0.5. Раз 2D-детекции нет, нет и точки по глубине — объект для системы просто не существует.
- Как обнаружить снова: в `metrics.json` у `sample-05` `objects: []`, хотя в аннотации один объект; FN в отчёте. Проверять recall отдельно на тёмных и слабо освещённых кадрах. Порог по test не подбираем — иначе оценка снова станет нечестной.

## 3. Ложная красная компонента

- Кадр: `sample-06`. Кроме размеченного объекта `[4, 3, 2, 2]` (он найден, IoU 1.0), в левом верхнем углу красная полоска фона `(255, 0, 0)` в пикселях (0, 0) и (0, 1).
- Причина: площадь полоски 2 пикселя, это ровно `min_area_px`, цвет проходит порог — baseline считает её конусом и выдаёт bbox `[0, 0, 1, 2]`.
- Влияние: FP +1, precision 0.5. У этой детекции `matched: false`, `iou: 0.0`.
- Как обнаружить снова: в отчёте предсказания с `matched: false`; FP. Отдельно смотреть детекции у края кадра и очень маленькой площади.

### Почему правильная проекция не делает её конусом

Для ложной детекции evaluator и наша нода честно считают точку: пиксель `u = 0`, `v = 1`, глубина 1000 мм → `X = (0 − 3.5)·1/8 = −0.4375`, `Y = (1 − 2.5)·1/8 = −0.1875`, `Z = 1.0` м. Формула верна: это действительно точка поверхности на этом луче, в метре от камеры. Но проекция переводит пиксель в пространство и ничего не говорит о том, *что* там находится. Что это конус, решил детектор по одному цвету, и решил неверно. Правильная геометрия ложной детекции даёт точное положение фона, которое потребитель примет за препятствие в метре слева впереди.

## mean_iou = 1.0 в обоих отчётах

`mean_iou` считается только по сопоставленным TP. После исправления он остался 1.0, хотя одна детекция ложная и один объект пропущен: пропуск и FP в IoU не попадают. Высокий mean_iou не означает хорошего детектора.

## Ошибка в ROS-обёртке, найденная на живом показе

Не ошибка детектора, а моей ноды: при отправке кадра без depth нода ответила `stamp_mismatch` вместо `missing_depth`, потому что в буфере лежала depth прошлых кадров. Исправлено в `2bccbbc`, регрессионный тест `test_old_depth_in_buffer_is_missing_not_stamp_mismatch`. Подробно — `ros-demo.txt`.
