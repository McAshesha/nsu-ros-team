Задание: https://ros.lms.ci.nsu.ru/practices/pr08.
Работа выполнена в **существующем** контейнере `practical_hofstadter`,
Ubuntu 24.04 / ROS 2 Jazzy, рабочая папка `/workspaces/ros`.
Это тот же каталог, который в Windows находится в `C:\5sem\ros`.

## 1. На что направлена лабораторная

Роботу недостаточно знать, насколько повернулись колёса: ошибка одометрии
накапливается. Нужно связать его локальную систему координат с готовой картой.
ПР08 учит запускать локализацию AMCL, правильно соединять системы координат
и доказывать результат измерениями, а причину отказа — контролируемым опытом.

В этой работе карта уже дана. AMCL определяет положение на ней по лидару
и относительному перемещению из одометрии. SLAM, построение маршрута,
Nav2 planner/controller и движение к заданной цели в работу не входят.

Три стадии задания:

1. Собрать `map_server`, `amcl` и lifecycle manager в одном запуске.
2. Заменить только `base_frame_id: base_link` на `chassis`, которого нет в TF.
3. Вернуть `base_link`, воспроизвести ту же запись и измерить восстановление.

Критерии: после 10 секунд разгона за 20 секунд получить 200 запросов TF,
доступность не ниже 95%, не меньше 10 сообщений `/amcl_pose`
и медиану `covariance[0] + covariance[7]` не больше 0,25 м².
Фактические итоговые значения находятся в `localization.json`.

## 4. Устройство системы

```text
map.yaml + map.pgm ── map_server ── /map ────────┐
                                               │
bag ── /vehicle/scan ───────────────────────── AMCL ── /amcl_pose
bag ── /tf: odom → base_link ──────────────── tf2 │
bag ── /tf_static: base_link → lidar_link ─── tf2 └── /tf: map → odom
bag ── /clock ── общее время всех нод

lifecycle_manager_localization ── configure / activate ── map_server, amcl
measure_localization ── читает /clock, /amcl_pose и TF ── localization.json
```

### Карта и системы координат

`map.pgm` — изображение занятости: 52×24 ячейки, 0,25 м на ячейку.
`map.yaml` содержит путь к изображению, разрешение, начало `[-2.5, -3, 0]`
и пороги, по которым map server различает занятые и свободные ячейки.
Асимметричные выступы у стен помогают различать положение вдоль коридора.

| Связь | Смысл | Единственный владелец при записи | При replay |
| --- | --- | --- | --- |
| `map → odom` | Привязка локальной одометрии к глобальной карте | В ПР07 отсутствует | AMCL, `/tf` |
| `odom → base_link` | Положение корпуса по одометрии; непрерывное, но может дрейфовать | Адаптер одометрии ПР07 | rosbag2 player из записи, `/tf` |
| `base_link → lidar_link` | Постоянное положение лидара относительно корпуса | robot_state_publisher из URDF ПР06 | rosbag2 player из записи, `/tf_static` |

`map` — глобальная карта; её поправки могут скачком исправлять накопленную
ошибку. `odom` удобна для плавного локального движения.
`base_link` жёстко связан с корпусом, `lidar_link` — с датчиком.
Запрос `lookup_transform('map', 'odom', Time())` получает положение системы
`odom` относительно `map`; нулевое время означает последнюю доступную связь.

AMCL вычисляет глобальную оценку корпуса и сопоставляет её с одометрией:
`T_map_odom = T_map_base × inverse(T_odom_base)`.
Поэтому он публикует поправку `map → odom`, а не вторую одометрию.
Для сопоставления лучей лидара с картой ему также необходима связь
между `lidar_link` и настроенным `base_frame_id`.

### Как работает AMCL

AMCL хранит множество гипотез положения — частиц. Одометрия перемещает
их по модели движения с шумом. Для каждой гипотезы сравниваются лучи
лидара с препятствиями карты; согласованные гипотезы получают больший вес.
При пересэмплировании более вероятные гипотезы получают больше частиц.
Adaptive Monte Carlo Localization меняет их количество по неопределённости.

Используется обязательный профиль курса, без подгонки под успешный результат:

| Параметры | Значения и назначение |
| --- | --- |
| `use_sim_time` | `true`: время берётся из `/clock`, а не из часов компьютера |
| `base_frame_id`, `odom_frame_id`, `global_frame_id` | `base_link`, `odom`, `map`: связывают алгоритм с TF-деревом |
| `scan_topic`, `map_topic` | `/vehicle/scan`, `/map`: источники наблюдений и карты |
| `robot_model_type` | `nav2_amcl::DifferentialMotionModel`: обязательная модель шума приращений одометрии; это не контроллер руля Ackermann |
| `alpha1..alpha4` | По `0.2`: коэффициенты ошибок вращения и поступательного движения в модели одометрии |
| `alpha5` | `0.2`: параметр, применяемый омнинаправленной моделью; здесь она не выбрана |
| `laser_model_type` | `likelihood_field`: оценка луча по близости его конца к препятствию карты |
| `laser_likelihood_max_dist` | `2.0` м: предел расстояний поля правдоподобия |
| `laser_min_range`, `laser_max_range` | `0.12`, `20.0` м: используемый диапазон измерений |
| `max_beams` | До 90 лучей для одного обновления вместо всех лучей скана |
| `min_particles`, `max_particles` | От 500 до 2000 частиц |
| `pf_err`, `pf_z` | `0.05`, `0.99`: параметры адаптивного выбора числа частиц по KLD |
| `resample_interval` | `1`: пересэмплирование после каждого обновления фильтра |
| `update_min_d`, `update_min_a` | `0.05` м и `0.05` рад: минимальные перемещения для обновления |
| `sigma_hit` | `0.2` м: ширина модели согласованного попадания луча |
| `z_hit`, `z_rand` | По `0.5`: веса совпадений с картой и случайных измерений |
| `z_short`, `z_max` | `0.0`: соответствующие компоненты полной beam-модели здесь не используются |
| `do_beamskip` | `false`: пропуск несогласованных лучей этим механизмом отключён |
| `tf_broadcast` | `true`: AMCL публикует `map → odom` |
| `transform_tolerance` | `0.2` с: преобразование публикуется с временным запасом вперёд |
| `save_pose_rate` | `-1.0`: сохранение последней позы отключено, чтобы повтор начинался одинаково |
| `set_initial_pose`, `always_reset_initial_pose` | `true`: применяется заданная начальная гипотеза, при повторной активации она сбрасывается |
| `initial_pose` | `x=0`, `y=0`, `z=0`, `yaw=0`: одинаковая стартовая гипотеза во всех опытах |

Официальная справка:
https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/others/configuring_amcl/.

### Зачем lifecycle manager

Наличие процесса ещё не означает, что нода обслуживает данные.
Сначала manager вызывает настройку `unconfigured → inactive`,
затем активацию `inactive → active`. Порядок: `map_server`, затем `amcl`.
В профиле заданы `autostart: true` и `node_names: [map_server, amcl]`.
Это автоматически загружает карту и запускает локализацию.
Проверка `ros2 lifecycle get` сохранена отдельно для обоих процессов.
Связи bond позволяют manager отслеживать жизнеспособность управляемых нод.

Справка:
https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/configuring_lifecycle_manager/.

### Зачем Python, CMake и зависимости

`rclpy` — Python-интерфейс ROS 2: нода, параметры и подписки измерителя.
`geometry_msgs` описывает позу и ковариацию; `rosgraph_msgs` — `/clock`;
`sensor_msgs` — скан; `nav_msgs` — одометрию; `tf2_ros_py` — буфер преобразований.
`rosbag2_py` читает MCAP для аудита; `rosidl_runtime_py` находит классы типов
сообщений, `python3-yaml` читает YAML.

`ament_cmake` оформляет установку ROS-пакета. Код нод здесь Python,
поэтому поиска C++-библиотек Nav2 в CMake нет. `install(DIRECTORY ...)`
помещает настройки в `share/localization_case`, а `install(PROGRAMS ...)`
делает скрипты доступными для `ros2 run`.
`ament_index_python` находит установленный пакет независимо от текущей папки.
`launch` и `launch_ros` описывают аргументы и запускаемые ROS-процессы.

`hashlib` вычисляет SHA-256, `json` сохраняет машинный отчёт,
`statistics.median` вычисляет медиану, целые наносекунды задают точные границы.
Вспомогательный Python запускает отдельные группы процессов и завершает
их сигналом SIGINT, аналогом `Ctrl+C`.
График строят Matplotlib, NumPy и Pillow; pytest проверяет измерение.

## 5. Как выполнено измерение

Измеритель запускается раньше player и сообщает `READY`.
Первый полученный `/clock` становится `t0`; в этой записи это 157,763 с.
Последний `/clock` — 188,333 с, разность — 30,570 с.
Окно оценки: **[167,763; 187,763) с**, а не абсолютные [10; 30).

В каждом интервале длиной 0,1 с внутри окна выполняется один настоящий
`lookup_transform('map', 'odom', Time())`. Исключение TF считается неудачей.
Результат — число успехов, делённое на все 200 запросов.
Программа не заменяет пропуск несколькими запросами подряд. Если пропущен
интервал, запись слишком короткая или `/clock` пошёл назад, опыт отклоняется.

Для ковариации берутся сообщения `/amcl_pose`, чей **header.stamp** попал
в то же полуоткрытое окно. Матрица имеет размер 6×6 и развёрнута построчно:
элемент 0 — дисперсия x, элемент 7 — дисперсия y. Складывается именно эта
пара элементов каждого сообщения, затем вычисляется медиана сумм.

`localization.observations.json` содержит каждый запрос, его время и результат,
позы, ковариации, задержки сенсорных stamp и несколько сканов,
преобразованных в `map` именно на время скана. `localization.png`
построен по этим наблюдениям.

Дополнительные запросы во время разгона сохраняются отдельно как
`warmup_queries` и не входят в 200 запросов обязательного окна.
Они позволяют увидеть отсутствие TF в коротком дефектном опыте.

Replay замедлен через `--rate 0.5`: это даёт процессам больше настенного
времени, но не меняет окно в секундах симуляции. `--clock` не добавляется:
часы уже записаны в bag. `--loop` не используется, чтобы время не шло назад.

QoS подписки измерителя на `/clock` — `best_effort` с глубиной 100:
такая подписка совместима с часами моста ПР07 и с replay, а очередь
сохраняет первые сообщения при короткой задержке обработки.
Для сенсоров используется `sensor_data` QoS. `/tf_static` воспроизводится
с `transient_local`, поэтому поздний подписчик получает постоянные связи.
`/map` также использует сохранение последнего сообщения для поздних подписчиков.

## 6. Дефект и доказательство исправления

Между `amcl.yaml` и `amcl-defect.yaml` отличается ровно одна строка.
В TF нет системы `chassis`. AMCL не может выразить скан `lidar_link`
в системе корпуса и построить требуемую оценку.
Смена карты или переустановка Nav2 не создаёт отсутствующую связь TF.

Подробные команды, первая ошибка, владельцы связей и численные результаты
находятся в `tf.md`, вывод процессов — в `defect-launch.txt` и `fixed-launch.txt`.
Перед каждым опытом перезапускаются localization, player и измеритель.
Так удачный transform из прошлого опыта не может скрыть ошибку нового.
В дефектном опыте сначала останавливается локализация, пока player ещё
публикует время, и только затем player: это избегает зависания ожидания
отсутствующего transform при остановленных часах в Jazzy.

Короткий дефектный опыт намеренно не выдаёт итоговый `localization.json`:
он не обязан пройти 30-секундное окно. Его сообщение `INVALID EXPERIMENT`
означает, что короткие данные не выданы за полноценный замер.
Факты отказа сохраняются в `defect.observations.json` и логах.

В RViz проверено наложение красных точек `/vehicle/scan` на стены `/map`
с `Fixed Frame=map`. В журнале программного OpenGL был GLSL warning,
при этом карта и скан отображались. Есть также независимый сохранённый
график наложения `localization.png`.

Доступность последнего TF не доказывает свежесть каждой связи.
Низкая ковариация означает уверенность фильтра, а не измеренную абсолютную
ошибку координат. Независимая ground truth-траектория не использовалась.
В `tf.md` отдельно приведены stamp и задержки сенсоров относительно `/clock`.

## 7. Как повторить в существующем контейнере

Из PowerShell открыть Bash в **том же** контейнере:

```powershell
docker exec -it -w /workspaces/ros practical_hofstadter bash
```

Дальнейшие команды выполняются в Bash контейнера:

```bash
source /opt/ros/jazzy/setup.bash
cd /workspaces/ros
colcon build --symlink-install --packages-select localization_case
source install/setup.bash
colcon test --packages-select localization_case --event-handlers console_direct+
colcon test-result --test-result-base build/localization_case --verbose
```

`source` подключает ROS и поверх него установленные пакеты workspace.
`--symlink-install` использует ссылки на исходники, где это поддерживается.
`--packages-select` ограничивает сборку новым пакетом.
`console_direct+` выводит подробности тестов сразу.

Перед replay остановить Gazebo, мост и управляющие ноды.
Автоматический повтор всех трёх стадий:

```bash
export ROS_DOMAIN_ID=169
python3 tools/pr08/run_experiments.py --rate 0.5
```

Домен изолирует граф ROS от других экспериментов. Можно повторить только
одну стадию через `--only baseline`, `--only defect` или `--only fixed`.
Программа использует `--no-daemon` при проверке состояния и издателей,
чтобы опираться на заново обнаруженный граф.

Ручной запуск, по одной команде в трёх терминалах с одинаковым окружением:

```bash
# A: карта, AMCL, lifecycle manager
ros2 launch localization_case localization.launch.py \
  params_file:=$PWD/src/localization_case/config/amcl.yaml \
  map:=$PWD/evidence/pr08/map.yaml

# B: дождаться READY; после конца replay остановить Ctrl+C для сохранения
ros2 run localization_case measure_localization.py

# C: запускать только после READY в B
ros2 bag play fixtures/pr07-sensors --rate 0.5
```

В `launch` аргумент `map` преобразуется в абсолютный путь и передаётся
map server параметром `yaml_filename`. `params_file` выбирает YAML.
Для дефекта укажите `amcl-defect.yaml`, не меняя других входов.

Визуализация во время исправленного replay:

```bash
rviz2 -d src/localization_case/rviz/localization.rviz \
  --ros-args -p use_sim_time:=true
```

`-d` выбирает настройки RViz; `--ros-args -p` задаёт параметр ROS.
В окне проверяются карта, скан и связное дерево TF.

Проверка сохранённых результатов:

```bash
ros2 run localization_case inspect_recording.py fixtures/pr07-sensors
python3 tools/pr08/plot_results.py
python3 tools/pr08/write_report.py
python3 .course-kit/v1/tools/validate_localization.py \
  evidence/pr08/localization.json \
  --schema .course-kit/v1/fixtures/pr08/localization-result-v1.schema.json \
  --map-yaml evidence/pr08/map.yaml --map-pgm evidence/pr08/map.pgm
python3 .course-kit/v1/tools/check_practice.py PR08 --submission .
```

Первый валидатор проверяет не только JSON-синтаксис: также типы,
пороги, отношение успехов к запросам, размер окна, длительность и хэши карты.
Последний checker дополнительно проверяет оформление сдачи и историю Git.

## 8. Оформление сдачи

Реализация, конфигурация, инструменты и CI входят в первый коммит.
Второй содержит результаты и декларацию ИИ. Поле `commit` в
`report.json` указывает на первый коммит. Вывод проверки сохранён
в `check-practice.txt`.
